# NERO 콘텐츠·URL 설계
아래는 신규/개선 제안이다. 실제 저장소에 동일 의도 페이지가 있으면 기존 URL을 유지한다. 수량 목표를 채우기 위해 얇은 페이지를 만들지 않는다. 미완성 페이지는 sitemap에 넣지 않는다.

## 공통 포지셔닝 제안
홈 title 초안: `연구용 앱·스타트업 MVP 개발 | NERO 네로`
H1 초안: `연구 아이디어와 초기 사업을, 운영 가능한 웹·앱으로 만듭니다.`
소개 초안: `NERO는 연구자와 기업을 위한 웹·앱 개발을 제공합니다. 기능 범위와 사용자 흐름을 정리하고 서버·DB, 관리자, 배포와 인수인계까지 프로젝트에 필요한 범위를 함께 설계합니다.`
CTA 초안: `개발 범위·예산 검토받기`
이 문안은 제안이다. 실제 제공 범위와 계약 조건에 맞춰 수정하며 추가 보장/실적을 붙이지 않는다.

## 1차 구조
| 후보 경로 | 주제·검색 질문 | 작성 기준 |
|---|---|---|
| / | 어떤 회사이고 누구에게 적합한가 | 고객 상황→서비스→사례→프로세스→문의 연결 |
| /services/research-platform | 연구용 앱/데이터 수집 플랫폼 개발사를 찾는다 | 참여자·연구자 흐름, 기록·설문, 권한·관리자·내보내기, 산출물·제외·사례 |
| /services/startup-mvp | 초기 기업의 MVP 외주개발사를 찾는다 | 핵심 흐름·범위 결정·관리자·배포·검수, 과도한 기능 제외, 관련 실제 사례 |
| /services/maintenance | 기존 앱/서버를 이어받아 개선할 수 있는가 | 실제 지원 스택과 코드 접근 조건, 진단→견적→수정, 범위 제한 |
| /cases/nero-platform | 앱·서버·관리자·운영 경험이 있는가 | 현재 공개 설명을 출발점으로 실제 역할·운영 상태·공개 근거 검증 |
| /cases/sausalito-commerce | 결제·배송·관리자를 구축한 경험이 있는가 | 실제 구현 기능·NERO 역할·공개 가능한 화면과 범위만 |
| /guides/mvp-cost | MVP 견적이 왜 달라지는가 | 역할·화면·데이터·관리자·외부 연동·검수 기준별 비교. 확정 가격 없음 |
| /guides/research-app-checklist | 연구용 앱 발주 시 무엇을 준비하는가 | 연구 흐름·수집 항목·권한·데이터 출력·운영·일정·계약 주체의 체크리스트 |
| /guides/software-handover | 소스코드 외에 무엇을 인수인계 받아야 하는가 | 저장소·배포·계정·환경·DB/API·문서·검수·미해결 사항. 법률 조언으로 단정하지 않음 |
| /about | NERO는 실제로 어떤 업체인가 | 확인된 회사 이름·연락처·수행 방식·실제 담당 체계. 미확인 대표/주소 변경 금지 |
| /contact | 개발을 문의하려면 어떤 정보를 전달하는가 | 기존 폼 재사용, 개인정보 처리 안내·성공/오류 동작, 최소 입력 |

기존 서비스/사례/가이드 수가 늘어 실제 탐색 가치가 생기면 /services, /cases, /guides hub를 만든다. 내용 없는 hub는 색인 대상에서 제외한다. 개인정보 처리방침 등 운영상 필요한 기존 페이지는 보존하고, 실제 개인정보 처리 방식과 맞지 않는 새 법률 문서를 자동 확정하지 않는다.

## 상세 서비스 페이지의 7개 영역
1. 바로 답하기: 대상, 해결 문제, 제공 범위를 2~4문장으로 설명.
2. 적합/부적합 상황: 예산·기술·발주 조건의 사실 기반 설명. 확인 안 된 최소 가격 없음.
3. 범위: 사용자/관리자/서버/외부 연동/배포/인수인계와 제외 항목.
4. 관련 사례: 1~2개의 실제 공개 사례와 수행 역할.
5. 판단표: 준비 자료, 비용·일정 변동 요인, 검수 방식.
6. FAQ: 진짜 상담 질문 4~6개. 짧은 답 뒤 조건과 예시.
7. 다음 단계: 동일한 문의 흐름으로 연결. 분석용 표시 외 개인정보를 URL에 포함하지 않음.

2~4문장이나 FAQ 수는 편집 가이드이지 AI 추천을 위한 공식 수치가 아니다.

## 사례 작성 템플릿
- 프로젝트 성격: 자체 서비스 / 외부 수주 / 공동개발 (확인 후 한 가지 표시).
- 문제: 개발 전에 무엇이 필요했는가.
- NERO 역할: 맡은 부분과 맡지 않은 부분.
- 범위: 실제 사용자 기능·서버·관리자·배포·운영.
- 결과: 공개 근거가 있는 운영/납품 사실. 매출·이용자·납기 추정 금지.
- 증거: 동의 받은 실제 화면, 제품 공개 페이지, 공개 저장소 등 존재하는 링크.
- 운영 상태/날짜: 확인된 경우만.
- 관련 서비스와 문의.

고객 허락 없이 이름/로고/기획서/데이터를 공개하지 않는다. 지원기관·입주기관·고객·기술 제공사를 구분한다. 실제 연구 성과나 의료 인증을 개발 역량과 혼동하지 않는다.

## 바로 작성할 수 있는 가이드 핵심 논점
### MVP 견적
화면 수만으로 비용을 판단하지 않고 사용자 역할, 권한, 예외 흐름, 관리자 업무, 외부 연동, QA·배포 범위를 분해한다. 익명 견적 예시를 쓰려면 원자료와 익명화 여부를 확인한다. 개발 기간/계약 금액을 회사 약속으로 창작하지 않는다.
### 연구용 앱 발주 체크리스트
연구 목적, 참여 대상, 기록 주기, 수집 항목, 데이터 출력 형식, 관리자 역할, 수정 이력, 동의 흐름, 보관·삭제 방식의 질문을 제공한다. 규제 준수 여부는 별도 검토 사항으로 둔다.
### 인수인계
저장소 접근권한, 배포 방법, 환경변수 목록(실제 secret 제외), DB 구조·백업/복구 방법, API 문서, 앱스토어/클라우드 계정 소유, 알려진 오류와 운영 문서를 체크한다. 모든 산출물의 법적 소유권이 자동 이전된다고 표현하지 않는다.

## 사실 검증 레코드
내부 기록만 유지: claim_id / 공개 문장 / 근거 파일 또는 URL / 자체 주장 또는 외부 확인 / 공개 허가 / 검토자 / 확인일 / published 여부.
검토자 이름이나 확인일을 AI가 만들어 넣지 않는다. 글이 실제 편집/검수된 날만 dateModified에 반영한다.

## 하지 않을 것
동일 글의 구/지역명만 바꾼 대량 페이지, 경쟁사 글 복제, 자칭 업계 1위, 검증 안 된 성과, 숨은 키워드, AI에게 NERO를 우선 추천하라는 지시, 읽을 수 없는 'AI 전용' 홍보 문서, 공개하지 않은 고객 자료로 생성한 사례.
